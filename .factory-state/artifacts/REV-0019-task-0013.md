## How the rules were applied
- Layering: the protocol client is a pure engine module (no database, no settings; the caller passes the spec and timeout). `McpService` holds permissions, secrets, URL policy, discovery cache and argument coercion. The repository has queries only. Routes delegate. Runs reach the service through `Ports`.
- DRY: the SSRF guard and IP pinning are shared with webhooks (`public_address`, `pinned_request`; `resolve()` now delegates). Scopes reuse the approval-channel model, and secrets reuse the credential Fernet key and masking.
- KISS: own minimal client instead of the SDK, one session per call, discovery cached in the row.
- Envelope + English codes: 12 `MCP_*` codes (catalog, `docs/api-errors.md`, en/vi). Node errors carry the code.
- Migration `0020` on SQLite and Postgres (pgvector/pg17, plain 16 in CI runs).
- Strict shadcn: new `--node-mcp` token; the Retriever token moved to hue 150 (it was close to the Code node). Only shadcn components; the stdio arguments use the shadcn `Textarea`.

## Security
- stdio is off by default and admin-only; the process gets a clean environment (the studio's secrets are not inherited), a temp home, a timeout and a process-group kill.
- HTTP: public addresses only unless allowed; the connection is pinned to the validated IP; no redirects.
- Secrets are encrypted at rest (a test checks the stored column), write-only through the API and masked in the UI.
- Personal servers are invisible to other users. Org servers can be used by everyone but managed only by admins.

## Open issues
- Each stdio call starts a process (about 100 ms for Python, more for `npx`). A pooled session per run could follow if latency matters.
- No OAuth flow for HTTP servers that require it; static headers only.
- Tools only (no resources or prompts). The tool list is a snapshot: re-run discovery after a server update (the node also re-discovers once when a tool is missing).
