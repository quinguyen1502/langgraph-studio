## How the rules were applied
- Layering: pure engine modules (`embeddings`, `documents`, `ports`). One repository owns the SQL, including the pgvector and brute-force paths. `KnowledgeService` holds the rules: ownership, limits, embedder consistency, and the run-time retriever. Routes only delegate.
- The engine reaches services only through `Ports`, which TASK-0013 will reuse for MCP calls, so node executors stay testable with plain functions.
- DRY: embeddings reuse the LLM HTTP helper (`llm._post`, the same mockable client) and the credential resolver. The locale and error-doc updates are scripted from the catalog.
- KISS: synchronous ingestion, an exact scan per knowledge base, no ANN index (see DEC-0021).
- Envelope + English codes: 12 `KB_*` codes in the catalog, `docs/api-errors.md` and en/vi. Retriever failures carry the code on the node error event.
- Migration `0019` checked on SQLite, Postgres 16 without pgvector (JSON fallback) and pgvector/pg17 (vector column), and on the existing compose volume.
- Strict shadcn: the new `--node-retriever` token in light and dark; only shadcn components and tokens.

## Security
- Owner-only knowledge bases. Another user's id is `KB_NOT_FOUND`, in the API and in runs. Embedding keys are the existing encrypted credentials, resolved for the knowledge base's owner only; they are never returned.
- Uploads: extension allow-list, 10 MB cap enforced on the bytes read, only the base name is kept. PDF parsing errors become `KB_FILE_UNREADABLE` without stack traces.

## Open issues
- No ANN index yet: fine for thousands of chunks per knowledge base, revisit for very large ones.
- Ingestion blocks the request: a 10 MB PDF with the OpenAI embedder takes a few seconds. It could move to the job queue later.
- Scanned PDFs (no text layer) are rejected as empty; OCR is out of scope.
- Knowledge bases are not shared yet (TASK-0014).
