## Security review
- Callbacks are authenticated before parsing: Slack HMAC with a timestamp window, Telegram secret header, constant-time compares.
- The decision and expiry are inside the HMAC. The token is bound to the channel connection it was posted through (`channel_id` must match).
- The Slack `response_url` is only called on `https://hooks.slack.com/`.
- Secrets are never returned (masked hint only). The callback URL contains only the opaque channel id.

### Security notes
- Codes: 6 digits from `secrets`, HMAC-stored, single pending code, expiry, attempt cap, resend throttle. A verified link elsewhere blocks verification (`IDENTITY_TAKEN`). Unverified links grant nothing.
- Org channels: only admins write them. A node can only use its owner's personal connection or an org connection, never another user's personal one.
- Shared Slack URL: the claimed `team.id` only selects candidate secrets, and the signature still decides. An unknown team gets the same 401 as a bad signature.
- Rate limits run before any decryption or HMAC work. The IP comes from the last XFF hop only when `STUDIO_TRUST_PROXY=1`.

### Remaining issues
See DEC-0019 "Remaining limits": approvers need a usable connection to get a code; Slack ids are assumed unique across workspaces; a narrow race between two users verifying the same account; a studio-UI resume of an API run does not re-send `callback_url`; single-proxy XFF trust; no Enterprise Grid / OAuth distribution; admins are managed by environment variable only.
