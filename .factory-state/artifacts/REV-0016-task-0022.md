## How the rules were applied

| Rule | Where |
|---|---|
| Layered | Adapters (platform HTTP only) sit under `ApprovalService` (rules), which uses `ApprovalRepository` (data). The route only reads the raw body and headers. `RunService` and `RunWorker` know only the service hooks. |
| DRY | One token, authorization and audit path for every channel. The resume reuses `plan_resume`, `claim` and `execute`. Secrets reuse `core/crypto`, and the token key is derived from the same secret key. |
| SOLID/KISS | Open/closed: a new channel is one subclass in `ADAPTERS`. Single use is one compare-and-set on a status column. One channel per node. |
| Envelope + codes | 13 new codes in CATALOG, docs/api-errors.md, en and vi. Callback refusals are envelope 200 with `code`. |
| Strict shadcn | Dialog, Tabs, Table, Badge, Input, Label, Select, Separator and Alert only; theme tokens, no hardcoded colours. |
| Alembic | `0010_approval_channels`, idempotent; tests pass on SQLite and Postgres, and Compose is at head 0010. |

## Security review
- Callbacks are authenticated before parsing: Slack HMAC with a timestamp window, Telegram secret header, constant-time compares.
- The decision and expiry are inside the HMAC. The token is bound to the channel connection it was posted through (`channel_id` must match).
- The Slack `response_url` is only called on `https://hooks.slack.com/`.
- Secrets are never returned (masked hint only). The callback URL contains only the opaque channel id.
