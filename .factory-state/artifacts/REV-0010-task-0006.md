## How the rules were applied

| Rule | Where |
|---|---|
| Layers | Engine: `Interrupt`, `human` node, `entry`/`resume` in compiler and runtime (no DB). Service: `plan_resume`, `pending`, `cancel_waiting`, checkpoint in `record`. Repository: `get`, `list_waiting`, upsert `add`. Routes: `GET /api/runs/pending` only calls the service. |
| DRY | One socket path in the UI (`stream()`) for new and resumed runs. One trace builder handles `run_waiting` / `run_resumed`. One `record()` for every run end (finished, waiting, cancelled while waiting). |
| KISS | Own JSON checkpoint instead of a LangGraph checkpointer per backend (DEC-0013). Text response only; approve/reject are the strings `approved` / `rejected`. |
| Envelope / codes | `RUN_NOT_WAITING`, `RUN_RESPONSE_INVALID` in catalog, docs and en/vi. Ownership failures reuse `RUN_NOT_FOUND`. |
| shadcn / tokens | Alert, Button, Textarea, Card, Badge. New theme token `--node-human` (light/dark), no raw colours. |

## Findings / open

- Run duration includes the human wait (wall time); node spans show the real work.
- The workflow snapshot is stored in the checkpoint, so edits made while a run waits do not affect that run. This is intended, but undocumented in the UI.
- No notifications and no expiry for waiting runs.
- The new `useEffect` reads the `?run=` param; lint reports the usual exhaustive-deps warning (same pattern as the existing ones).
- E2E: one full-suite run had a navigation `ERR_ABORTED` flake in an existing spec. Two reruns of the full suite passed.
