## Findings

### Blocking

- None.

### Non-Blocking

- **Behaviour on errors is unchanged.** If `finish` raises (Redis down), the error leaves `execute` exactly as
  `afinish`'s did. A cancel while it runs raises `CancelledError`, as before, but the `DELETE` still completes.
- **`finish` on a thread instead of `redis.asyncio`.** This uses one connection from the sync client's pool for a
  single `DELETE` per run. The loop is not blocked, which is what DEC-0016 point 13 is for. Fine.
- **Removing `afinish` (KISS).** It has no caller left. Keeping an async twin that must not be used at run end would
  invite the same bug back.
- **The fenced path is unchanged:** a fenced worker still leaves the new owner's entry alone.
- **Test design.** Only the `(True, True)` case (disconnect, busy executor) fails on the old code. The `(False, False)`
  case passes on both, and stays as a guard for the cancel path.

## Standards And Architecture Alignment

- **Layers (DEC-0009):** the change stays in the services. No FastAPI, no SQL, no schema change.
- **DRY:** it reuses the TASK-0059 helper; its docstring now covers both kinds of write.
