## Findings

### Blocking

### Non-Blocking

- **Fixed during review: run bus race on scripted answers.** The suite queued the resume job inside `settled`, before
  the finished segment left the run bus, so a fast worker could register the next segment and then have it removed by
  the old segment's `finish` (cancel would miss it). The resume is now queued one second later (`enqueue_at`). Moving
  `settled` after `finish` was tried and dropped: it widened the window in which a WebSocket client that closes right
  after `run_summary` cancels the handler before the API callback is queued
  (`test_api_run_resumed_from_the_studio_sends_its_callback_once`).
- **Fixed during review: no extra await before API callbacks.** `settled` first read the run row to find test runs;
  the extra thread hop had the same effect on the WebSocket callback test. `settled` now takes the run's `source`
  from the plan or the job.
- **Fixed during review: name clash in `decisions.ask`.** A parameter named `mock` shadowed the `mock()` function;
  renamed to `offline`.
- **Email output shape.** The task text named `{"sent": false, "test": true, "message": …}`. The existing dry-run shape
  (`sent: false, dry_run: true`, recipients, subject, preview) is reused instead, so a workflow's next nodes see the same
  fields with or without a credential.
- **Stuck suites.** With the in-memory queue, a restart loses queued cases and the suite stays `running` until someone
  cancels it (Cancel always works). A resume job that cannot plan (e.g. the run expired) leaves its case running the
  same way. Recorded in DEC-0044; rare enough not to need a sweep.
- **Parallel limit** is counted per `_advance` call; two cases settling at the same moment can start one case more than
  `STUDIO_TEST_PARALLEL` for a moment. Each case still starts once (claim).
- **Imported workflows.** The Tests tab is hidden and the API refuses edits and runs (`TEST_NOT_SUPPORTED`); listing
  works.
