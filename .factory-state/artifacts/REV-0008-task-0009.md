## Findings / open

- Runs still execute in the API process holding the WebSocket; Redis is for cancel signalling and event fan-out. A real queue is deferred (needed for TASK-0007 webhooks).
- Redis calls in `emit` are synchronous (sub-millisecond on a local Redis); move to `asyncio.to_thread` if Redis is remote and slow.
- Startup migrations are not guarded against concurrent upgrades; keep one `api` replica (or run `alembic upgrade head` as a one-off job before scaling).
- Nothing subscribes to `run:{id}:events` in the app yet (observers / TASK-0010 can use it).
- The `api` image runs repo imports (git + uv) inside the container; isolation is still TASK-0015.

## Follow-up: TASK-0019 (phase-2 hardening, DEC-0016)

- **Resolved**: Redis calls on the event loop (`start/finish/publish` in `execute`/`emit`) now use `redis.asyncio`; blocking calls stay in threads.
- **Resolved**: startup migrations are serialised (Postgres advisory lock / SQLite file lock), so several `api`/`worker` replicas can start together.
- **Resolved**: a real queue exists (TASK-0007), now reliable with ack and stale-job recovery.
