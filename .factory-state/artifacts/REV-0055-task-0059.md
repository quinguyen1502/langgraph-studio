## Findings

### Blocking

- None.

### Non-Blocking

- **The same shape remains in `execute()`'s `finally`.** `await asyncio.shield(self.bus.afinish(rid))` is also a
  coroutine that a closing loop can cancel before it starts. With the Redis bus, the run's `owner` key then stays until
  its 24 h TTL. The run itself is recorded correctly, so no data is lost.
  - Side effect: until the key expires, a REST cancel of that run id is treated as "running elsewhere" and does not
    change the stored status.
  - Left as is; worth a small follow-up.
- **A first fix covered only the cancel path, and CI kept failing.** That showed the main cause was the second one,
  in the normal path. Both writes now share one helper, which also keeps it DRY.
- **The cancel path waits on the shielded write.** If `record` raises anything other than `StaleLease`, the
  error replaces the `CancelledError`, as before. Behaviour is unchanged apart from when the write starts.
- **`_fenced` now runs on the executor thread** in this path (it used to run on the loop thread). It only ends the
  trace span and logs, and the normal path already calls `record` on a thread. Fine.

## Standards And Architecture Alignment

- **Layers (DEC-0009):** the change stays in the service. No FastAPI, no SQL, no schema change.
- **Tests:** the regression tests drive `RunService.execute` directly with an in-memory bus and its own event loop.
  It shuts the loop down exactly as `asyncio.Runner` does, so it does not depend on CI speed.

## Validation Review

Evidence is in QA-0055. Each new test fails 3 out of 3 runs on the code it targets, and passes 3 out of 3 with the fix. The full
suites pass on SQLite and on a fresh Postgres 17 + Redis 7.
